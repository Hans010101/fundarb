# FundArb 产品与交易专业评审

## 结论

方向成立，但“同价同时平仓、两边盈亏自然抵消”不是可靠假设。真正的总损益至少包含资金费、四腿手续费、四腿滑点、基差变化、资金占用成本、币种折算和税务/合规成本。退出时应比较“继续持有的期望 carry”与“立即退出成本及尾部风险”，而不是等待费率差归零。

产品已从“研究雷达”升级为个人套保交易终端，但“具备真实交易代码”不等于“已达到无人值守生产标准”。正式开主网的闸门仍应是：历史回测在保守成本下有足够候选，Paper 记录预测费率与实际到账偏差，Testnet 完成异常路径演练，最后才是独立子账户小额 Live。

## 对附件方案的评价

值得保留：动态结算周期归一化、四维 PnL 归因、交易所为唯一真相源、先持久化意图再下单、AMBIGUOUS 不重发、难腿优先、腿差超时回滚、独立 risk 进程、HALT 文件与三道部署锁。

需要修正或补充：

1. Cloudflare 可以承担管理鉴权、加密凭证、交易意图和风控总闸，但交易所出口与持续对账必须放在固定 IP 主机；不能把 Worker 当成完整的无人值守双腿引擎。
2. “全链路免费数据源”不等于数据可用于审计。预测费率、最终结算费率和账户实际到账要分表记录。
3. `margin_ratio = equity / maintenance margin` 在不同交易所含义不一致，统一阈值前必须用各所官方字段和强平距离做校准。
4. 不应只按 24h 成交额评估流动性。真实执行需要同时测算目标数量的 bid/ask VWAP、冲击成本、最大可成交量和两个订单簿的更新时间差。
5. 资金跨所配置是核心问题。两边保证金无法实时净额结算，利润端可能有钱、亏损端却先被强平；需要现金缓冲、自动再平衡计划和单所风险上限。
6. 稳定币、交易所信用、地区限制、API 规则变化、合约下架和 ADL 是不可对冲的尾部风险。
7. “准原子”只能减少腿差，无法消除腿差。执行指标应同时记录未对冲 USD×秒，而不只记录持续时间。
8. FMEA 还应覆盖：交易所进入 cancel-only、标记价异常、指数成分失真、WebSocket 乱序、成交回报先于订单确认、API Key 被风控冻结、子账户划转延迟、保证金币种冻结、费率结算推迟、合约乘数变化和法域限制。

## 开源方案取舍

- Hummingbot 提供大量连接器、执行器抽象和 funding-rate-arbitrage 示例，适合参考接口与错误案例；公开 issue 仍能看到停止策略后重复平仓/重复成交等问题，因此不建议未经审计直接托管实盘。
- CCXT 适合公共行情、市场精度与历史资金费率归一化；实盘下单仍应直接使用官方接口，完整掌握 clientOrderId、错误码、reduce-only 与账户模式语义。
- Freqtrade 与 NautilusTrader 可借鉴回测、事件模型和配置工程，但不是可直接替代跨所双腿执行器的现成成品。

## 建议路线

### P0：研究与可行性（当前）

- 五所实时扫描与动态周期归一化。
- 保守成本参数、最小回本期数、成本后 APR 和基差显示。
- 采集历史费率、标记价和盘口快照，至少覆盖 90 天。
- 输出“理论信号、可成交信号、结算到账”三层漏斗。

### P1：Paper（至少 30 天）

- 模拟真实下单延迟、盘口 VWAP、部分成交和资金费最终结算。
- 统计净捕获率、预测偏差、基差 VaR、未对冲 USD×秒和各所资金缓冲。
- 只有净捕获率、回撤和异常路径达到门槛才进入 testnet。

### P2：固定 IP 执行器

- Python 3.12 asyncio；engine 与 risk 两个独立进程。
- SQLite WAL 事务账本，先写 intent 后产生副作用；交易所为真相源。
- 官方交易 API，clientOrderId 幂等；AMBIGUOUS 必须查单。
- 独立子账户、禁止提现、独立密钥、IP 白名单、每日名义硬上限。
- Testnet 完成断网、超时、部分成交、单腿拒绝、进程强杀和恢复演练。

### P3：小额 Live

- BTC/ETH 两个白名单、1x 杠杆、单组合小额、人工确认开仓。
- 四周内不扩大仓位；每期核对实际 funding、手续费、滑点和基差。
- 达到验收指标后再引入 SOL、自动开仓或更多交易所。
